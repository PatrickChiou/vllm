\begin{abstract}
Prefix caching avoids repeated prefill work, but its effectiveness depends on capacity, block granularity and workload locality. We implement a CPU trace executor within vLLM v0's online serving path, retaining scheduling, sequence management and virtual prefix-block allocation. We evaluate matched single- and multi-turn ShareGPT workloads over 108 configurations, reuse a validated eight-source, 51-configuration baseline study, and evaluate eight policies on two mixed-workload compositions. With LRU/block 16, matched single/multi means are 4.41\%/3.52\% at 0.05\,GiB. Coding-agent LRU exceeds LFU by 13.16\,pp. Highest observed mixed scores are RFIFO 60.25\% (skewed) and RFIFO 41.18\% (equal-token). A repository-reported five-mixture sweep adds hold/admission sensitivity. The current simulator passes 153 correctness tests including both API frontends after repairing workload-label transport through multiprocessing. Results characterize realized cache reuse under controlled trace replay rather than GPU latency or throughput; limited production windows and single-seed mixed comparisons constrain generalization.
\end{abstract}

\section{Introduction}
LLM serving repeatedly processes instructions, documents and conversation histories that share input prefixes. Prefill constructs attention key/value (KV) state; subsequent decoding extends it. Retaining identical full-prefix KV blocks lets later requests avoid redundant prefill. PagedAttention provides block-based memory management and sharing in vLLM \citep{kwon2023}. Which reusable blocks remain available depends on both workload arrival structure and eviction decisions under limited capacity.

Different workloads create different retention problems. Growing conversations often revisit recently extended histories; a common instruction may recur across many otherwise unrelated requests; document questions can concentrate reuse in short bursts. This motivates three questions: can CPU trace replay preserve the online serving control flow, how do capacity and block size affect realized sharing in homogeneous chat, and which eviction rules work across heterogeneous and mixed workloads?

We contribute an online trace executor, causal client and request/block metrics, then compare homogeneous chat, eight separate sources and eight policies under two mixtures. Policy orderings are configuration-specific.

\section{Background and Related Work}
A KV block depends on its preceding token prefix: identical chunks in different histories are not generally interchangeable. Reference-counted active blocks are not candidates for eviction; policies order unused cached content. LRU favors recent access, LFU allocator access frequency, and FIFO insertion order. Their usefulness depends on whether past recency, popularity or insertion age predicts future demand.

vLLM's PagedAttention addresses block allocation and sharing \citep{kwon2023}. SGLang uses RadixAttention for reuse across structured programs \citep{sglang}; Prompt Cache uses explicitly defined reusable modules \citep{promptcache}. CacheBlend addresses non-prefix retrieval chunks with selective recomputation \citep{cacheblend}, whereas our simulator retains exact full-prefix semantics. Mooncake studies KV-centric disaggregated serving \citep{mooncakepaper}; our use of released anonymous hashes does not reproduce its distributed architecture. We study replacement behavior inside an existing serving control path, not a new attention algorithm or GPU serving speedup.

\section{System Design and Implementation}
\subsection{Trace execution within online serving}
The online path preprocesses HTTP prompts, admits/schedules sequences, manages blocks and processes token outputs. Our \texttt{SimExecutor}/\texttt{SimExecutorAsync} replaces model execution with \texttt{Simulator.step}; the surrounding v0 components remain active. Workload metadata and executor selection are modified, so the scheduler is not claimed entirely unchanged. Figure~\ref{fig:architecture} contrasts the execution backends and illustrates exact prefix sharing.

\begin{figure*}[t]
\centering\includegraphics[width=.95\textwidth]{figures/system_prefix.pdf}
\caption{Retained online control path with GPU execution replaced by trace replay. Identical leading token blocks share KV state; a changed suffix is computed separately. Chained identity prevents sharing an identical local block after a different prefix.}
\label{fig:architecture}
\end{figure*}

The simulator consumes scheduled metadata, honors sampling flags and computed blocks, and returns compatible sampler outputs. Next-token selection follows output length, preserving progress after recomputation. Cached prompts recompute the final sampling token. Normal EOS/stop handling releases state; exact prompt tokens plus request IDs distinguish duplicate prompts with different replies.

No model weights, attention kernels or actual KV tensors are loaded. Configuration and tokenizer files remain necessary. Virtual KV bytes per block are
\begin{equation}
B_{\rm KV}=2 L H_{\rm KV}d_h b s,
\end{equation}
where $L$ is attention layers, $H_{\rm KV}$ KV heads per rank, $d_h$ head dimension, $b$ tokens/block and $s$ bytes/element. This geometry controls virtual capacity, not allocated GPU memory. The executor awaits synthetic costs of 0.01\,ms per uncached prefill token and 0.1\,ms per decode sequence-step. CPU/HTTP overhead and queuing remain real wall time. LoRA, prompt adapters, speculative decoding and multistep scheduling are unsupported in this executor.

\subsection{Client, traces and workload labels}
\texttt{TraceBuilder} reuses serving preprocessing and the model's chat template/tokenizer, with fixed date arguments. ShareGPT normalization enforces role ordering and filters whole conversations for context eligibility. Single-turn mode retains only the first user/reply pair; multi-turn retains all eligible turns. The two modes thus share the same initial conversations and first-turn prompts/target arrivals. Optional agent truncation retains a causal prefix.

The concurrency-limited client uses recorded times or seeded Poisson arrivals and waits for the preceding reply before each later turn. It validates text, token counts and finish reason; failures stop descendants. Dispatch lag distinguishes target from achieved arrivals.

Dataset-provided labels propagate through request, sequence and block metadata; no online workload classifier is implemented. A missing optional label remains \texttt{None}. We repaired an incomplete multiprocessing path by adding the label to the client method, pickled RPC request and engine-side submission, rather than dropping it or disabling the frontend. Both endpoints/frontends pass integrated request/block-label checks. A subsequent fix strips all model-configured stop IDs from recorded replies to avoid premature termination; it changes preparation, not historical prepared traces. Current simulator correctness evidence is 153 passing tests, including trace identity, batching, EOS, preemption/recomputation and eviction ordering. This validation is scoped to the simulator suite, not all GPU-dependent upstream tests.

\subsection{Custom eviction policies}
TLRU orders three tiers: one-shot/expired/over-budget blocks first, recent agent/Bailian blocks next, and cross-label shared blocks last; recency orders each tier. Its hold is 8 seconds and protected budget 1 of the current unused-block table. TFIFO uses the same label tiers with insertion order and no expiry. Both classify chat as one-shot in the implemented static rule.

HFIFO and HLRU are label independent: a block's first reuse promotes it, with FIFO ordering or recency plus hold/budget expiry. RFIFO defaults to 100 resolved block outcomes per label (first hit, or eviction without a hit). Once full, a window with at least 5\% hits (now configurable) admits new blocks to a protected FIFO tier if any label qualifies. Later hits do not promote already resident low-tier blocks. These rules prioritize victims rather than absolutely pinning protected content: if lower tiers are empty, a protected unused block is evicted. Heap/version bookkeeping usually costs logarithmic operations, with stale-pop/rebuild worst cases; RFIFO also stores100 outcomes per label. The new CLI threads RFIFO window/threshold controls through cache configuration, scheduler and allocator. Details appear in the appendix.

\section{Experimental Methodology}
\subsection{Workloads and controlled configurations}
Historical validated studies use Qwen/Qwen2.5-0.5B-Instruct and tokenizer revision \texttt{7ae5576\ldots}, CPU-only v0 online simulation. M2 recovers the documented absolute-capacity sweep:200 eligible ShareGPT conversations, context 4096, single/multi modes,0.05/0.10\,GiB,8/16/32 tokens per block, LRU/LFU/FIFO, target100 requests/s, concurrency/max-sequences64, think time 0 and seeds 0/1/2. This gives108 configurations. Byte capacity is held approximately constant across block sizes (whole-block rounding); no ratio-based fallback is mixed into these comparisons. M2-A reuses block 16 LRU cells from M2-B.

The separate-source Task 1 study uses 51 existing configurations with 16-token blocks, cache approximately 25\% of each source's distinct full-block working set and concurrency 8. Text sources are ShareGPT \citep{sharegpt}, four interleaved AgentBank tasks \citep{agentbank}, CC-Bench coding trajectories \citep{ccbench}, grouped QuALITY document questions \citep{quality} and Code Alpaca instructions \citep{codealpaca}. Bailian chat/coder and Mooncake tool-agent windows provide anonymized prefix hashes \citep{bailian,mooncake}. Contexts are 2048 for chat/AgentBank,8192 for coding/QuALITY,32768 for production hashes and 1024 for code. Text uses 2--3 arrival seeds; production windows use one.



Mixed trials use one common context 32768, block 16, cache ratio 0.10, target100 requests/s, concurrency 8 and think time 1 second. The skewed cohort reuses the original construction; the equal-token cohort takes each label's first causal prefix reaching260,000 prompt tokens, with final-turn overshoot recorded. Mixed preparation retags IDs, shuffles conversations and assigns new Poisson first-turn times, discarding recorded production times. All policies see identical prepared hashes/capacity in each mixture. Each starts a fresh server/cache; new policy order is randomized. We complete one seed per mixture for all eight policies before any optional repetition, totaling 16 runs. The two-core/8\,GiB environment and recorded run times favor complete required comparisons over large ablation products; no mixed confidence interval is inferred.

\subsection{Metrics, integrity and reproducibility}
For request $i$, sharing fraction is $f_i=C_i/P_i$, where $C_i$ and $P_i$ are cached and total prompt tokens. The primary aggregate is
\begin{equation}
S=\frac{\sum_i C_i}{\sum_i P_i},
\end{equation}
which differs from the mean-request fraction $N^{-1}\sum_i f_i$. We report percentage-point (pp) changes separately from relative changes against a nonzero, configuration-matched baseline. Repeated-seed means use sample SD; one-run mixed/production results have no variability estimate or significance claim.

A logical full block is identified by a SHA256 chain over the preceding prefix and current tokens. Hits count distinct requests skipping that block at initial prefill and include zero-hit blocks in the population. Decode-computed blocks are also observed; counts aggregate across cache residencies. Reuse gaps are monotonic wall time since the preceding distinct-request access \emph{sampled at successful hits}; they exclude missed reuse and are not unconditional recurrence distributions or GPU times.

Per-run manifests record commands, source/input fingerprints, versions, seeds, capacity and controls alongside raw request/block logs. Independent analysis checks complete cohorts, IDs, token arithmetic, hit/gap totals, causality and policy input/capacity equality. Interrupted attempts are retained and excluded. All 175 studied configurations pass exported consistency checks; raw request totals include repeated replays of the same cohorts, not independent dataset samples. New mixed trials additionally count successful eviction allocations with an opt-in wrapper that preserves allocator results/ordering; its isolated check passes. Historical M2/Task 1 eviction counts and all promotion counts are unavailable rather than inferred from misses.

\section{Experimental Results}
\subsection{Homogeneous conversation reuse}
At block 16 with LRU, single-turn sharing is (4.41 $\pm$ 0.01)\% at 0.05\,GiB versus multi-turn (3.52 $\pm$ 0.00)\%. At 0.10\,GiB, the corresponding means are (4.41 $\pm$ 0.01)\% and (4.71 $\pm$ 0.16)\% (Figure~\ref{fig:m2mode}). Each mode starts from 200 identical eligible conversations; single runs contain200 requests and multi runs608. All three arrival seeds use the same tokenized cohorts. These are observations under the documented64-concurrent-request load, not an assumption that multi-turn must improve sharing. Representative seed 0 request-fraction medians are 24.07\% single and 2.58\% multi; the logical-block hit median is zero in both. These populations differ from token weighting. At block 16 the two capacities hold 273/546 virtual blocks (4,368/8,736 tokens), small relative to 64 active sequence slots. A policy-independent diagnostic finds 4.65\% single-turn and 57.73\% multi-turn prompt tokens in full blocks seen in an earlier planned prompt. It omits decode blocks, availability and actual completion timing, so it is not a full-serving cache bound. The large multi-turn recurrence versus low realized sharing distinguishes existing overlap from retained state.



Per-request CDFs, block-hit counts and hit-associated gap distributions provide complementary populations (appendix). Long prompts receive greater weight than in a median-request statistic. Only complete prefixes surviving allocation pressure become hits. Arrival, concurrency and causal completion affect survival; this interpretation is not an isolated causal ablation.

\subsection{Capacity and block granularity}
At 0.05\,GiB, LRU scores at 8/16/32 tokens per block are 6.61\%, 4.41\%, 0.01\% for single-turn and 4.83\%, 3.52\%, 1.50\% for multi-turn. Doubling byte capacity changes block 16 LRU by +0.00\,pp (single) and +1.18\,pp (multi). Figure~\ref{fig:sensitivity} shows the other policies and seed variability; the complete36-cell mean/SD table is supplementary.

Coarser blocks lose short full-prefix matches and leave longer non-reusable tails. Capacity can preserve more prefixes, but scheduling/preemption may disrupt monotonicity. These proposed mechanisms are not overhead or GPU-efficiency measurements.

\subsection{Separate heterogeneous workloads}
Figure~\ref{fig:task1} uses the validated51-run study (21,834 successful requests, zero failures); the multiprocessing-only transport fix does not alter its direct-mode executor/cache decisions. Coding-agent LRU reaches 48.59\% versus 35.43\% for LFU and 47.35\% for FIFO, approximately 13.16\,pp above LFU. Growing contexts plausibly favor retention of recently added prefixes while frequency can favor older popular blocks; no mechanism ablation proves this explanation.

LFU leads the observed Bailian chat/coder windows (29.52\%/37.28\%) versus LRU 28.44\%/35.87\% and FIFO 26.75\%/32.88\%. Each has one run, so production-wide superiority is not established. QuALITY FIFO 50.35\% exceeds LRU 49.25\% and LFU 45.54\%, with small repeat counts. AgentBank LRU 50.55\% and LFU 50.47\% differ by only 0.074\,pp. Mooncake LRU 40.27\% and LFU 40.25\% nearly tie; FIFO 39.72\%. ShareGPT is seed-sensitive; Code Alpaca ties at 29.53\% for all policies. Cross-workload capacities/contexts differ, so these establish within-source choices rather than a causal workload ranking.

\subsection{Mixed-workload policies}
The skewed mixture contains 3,322 requests and 10,517,812 prompt tokens, with 12,360 virtual blocks. Its highest observed policy is RFIFO at 60.25\%, compared with strongest baseline FIFO at 49.12\%: +11.13\,pp, or 22.66\% relative using unrounded scores. This single-run margin has no SD/CI estimate.

The equal-token mixture contains 6,051 requests and 2,119,769 prompt tokens, with 8,043 virtual blocks. Its highest observed policy is RFIFO at 41.18\%, compared with strongest baseline LRU at 35.85\%: +5.33\,pp, or 14.87\% relative using unrounded scores. This single-run margin has no SD/CI estimate.

The aggregate improvements conceal category harm: RFIFO loses 14.72\,pp on skewed Bailian-coder and 4.83\,pp on equal-token Mooncake versus the strongest respective baseline. These historical runs used the pre-update prepared traces and implementation; they are not reruns of the new commit.

\subsection{Reported hold and admission sensitivity}
Commit \texttt{ad1d826542} reports 125 additional cells: five mixtures, 25 settings each, seed 0. TLRU/HLRU sweep holds 3/8/30\,s and budgets 0.25/1; RFIFO sweeps windows 20/100/500 and thresholds 2/5/20\%. LRU/LFU/FIFO/TFIFO run once per mix; HFIFO is absent. Capacity is 10\% of each distinct working set, block 16, concurrency 8, think time 1\,s. The upstream table reports zero failures and no clamping. Only rounded summaries/plots are available here; raw completion, cohorts and counts are not independently verified or pooled with the 175 validated historical runs. Execution order is fixed, not randomized.

The highest reported chat-heavy score is RFIFO window 500/threshold 5\% at 23.6\%; protected-heavy favors HLRU hold 8/budget 1 at 39.3\%. LFU leads template-heavy at 47.6\%, while HLRU hold 30/budget 1 reaches 27.8\% on trace-heavy and 40.1\% on balanced input. The 0.1\,pp trace margin over LFU is unresolved by rounding/seed uncertainty. Across five equally weighted mixtures, HLRU hold 30/budget 1 has the highest in-sample macro mean (32.4\%); RFIFO window 100/threshold 2\% has the smallest worst regret (6.9\,pp). Neither establishes a universally robust setting (Figure~\ref{fig:sweep}).



\section{Discussion and Limitations}
The experiments establish workload/configuration-dependent realized reuse, not one optimal eviction rule. Static labels can preserve useful agent prefixes in one composition while harming a returning conversational category in another; adaptive admission can alter that trade-off without a universal guarantee. Labels are known from data, not predicted. Hold expiration depends on real CPU queuing and HTTP/synthetic delay. Single-seed mixed comparisons, fixed time windows, first-eligible subsets, one cache ratio and absent repeated-seed sensitivity cells limit external validity. Changing mixture also changes selected cohorts and absolute bytes at the fixed ratio, so this is not a composition-only causal ablation. The new sweep explores hold/admission parameters on selected cohorts without held-out evaluation.

The simulator does not model logits, numerical model quality, GPU bandwidth/kernels, real device timing or distributed KV transfer. Reuse scores cannot be converted directly into GPU speedups. CDFs of realized hits exclude missed opportunities; transformed traces omit original agent prompts and shorten production outputs. All trace entries are loaded into memory. The additional sweep has rounded aggregates only; its provenance and lack of raw revalidation are separate from the historical checks. Small margins and selected-parameter means do not establish statistical or out-of-sample superiority.

\section{Conclusion}
The CPU executor preserves an active online scheduling/cache path while substituting trace tokens for model computation. Matched chat reuse changes with block/byte controls, while heterogeneous policies range from large coding-agent differences to near ties. Highest observed mixed policies are RFIFO on skewed and RFIFO on equal-token input, with single-seed uncertainty. The reported sweep further shows parameter-sensitive policy rankings. The findings support conditional policy selection and further controlled validation; they do not establish a GPU performance gain or universally best custom policy.

TLRU: classify each unused cached block as fixed, protected or cross-label shared; demote the oldest protected candidate to fixed competition when expired or above budget; evict the earliest tier's LRU victim. TFIFO: use static label tiers and FIFO serials without time/budget demotion. HFIFO/HLRU: begin unhit; promote on first own reuse; clear hit state on physical reuse; use FIFO or time-limited recency order. RFIFO: resolve a residency once on first hit or unhit eviction; append outcomes to each associated label's last100 entries; admit future blocks when any full label window reaches 5\% hits; evict low before admitted tier by insertion order. If no low blocks remain, protected blocks are still evictable. Active pinned blocks are outside the evictor.

Metadata includes label sets, insertion/frequency/hit state, versions and tier heaps; RFIFO additionally uses bounded per-label windows. Typical operations are logarithmic heap operations plus label/window work; lazy stale entries and periodic linear rebuilds mean worst-case latency is not strictly logarithmic. We do not report measured byte/CPU overhead or unavailable promotion counters. Mixed eviction counts come from a successful-allocation wrapper; older runs have no such counter. Full source mapping and limitations are in \texttt{POLICY\_DETAILS.md}.

# Eviction policies: implementation-grounded notes

Source: `vllm/core/evictor.py` at base commit3d501ab plus the final multiprocessing transport fix (policy decisions unchanged). B is the number of tracked cache blocks (including active/history metadata); L is the number of labels. The evictor heap operates on the unused candidate population plus stale entries. Active reference-counted blocks are excluded from the victim population. “Protected” changes victim priority, not pinning or an absolute refusal to evict.

| Policy | Priority / tie-breaking | Labels and shared blocks | Protection / history | Cost and metadata |
|---|---|---|---|---|
| LRU | Smallest last_accessed; deeper hashed prefix first on a recency tie | Labels recorded but not used to order | No protected tier | Lazy heap, normally O(log B) update/evict; stale-entry cleanup/rebuild can cost O(B) or multiple pops. O(B) block state subject to bounded heap cleanup. |
| LFU | Lowest allocator access frequency, then recency/insertion order | No label priority | Frequency survives pin/release, resets at eviction | Heap plus persistent insertion/frequency/version maps; typical O(log B), occasional O(B) rebuild. Exported logical hit count is a different metric. |
| FIFO | Lowest original insertion serial | No label priority | Pin/access does not refresh order | Same ordered-heap infrastructure and per-block history as LFU. |
| TLRU | Low tier before recent protected tier before cross-label tier; recency within tier, deeper prefix tie | Protected: agent/coding-agent/Bailian-chat/Bailian-coder. Chat/quality/code/Mooncake are low. Two+ labels form shared tier | Hold 8s/budget 1 in experiments. Oldest qualifying protected block drops into low competition when expired or over budget | Per-tier lazy heaps, versions, label sets and counts. Typical O(log B); stale pops and O(B) rebuild possible. Budget is a fraction of current free table. |
| TFIFO | Same label tiers; insertion serial within tier | Same protected/shared classification | No hold/budget expiry | Per-tier heaps/order/version/label maps. Typical O(log B), occasional O(B) rebuild. |
| HFIFO | Unhit before hit blocks; insertion order within tier | Label independent; no special cross-label tier | First own reuse promotes. Eviction clears the residency's hit | Hit-gate maps plus tier heaps; same amortized heap caveat. |
| HLRU | Unhit and expired/over-budget reused blocks compete by recency; fresh reused blocks last | Label independent; no shared tier | Hit promotion with 8s hold and budget 1 | Tier heaps, counts and per-block hit/version state; same heap/rebuild caveat. |
| RFIFO | Low before admitted tier; insertion order in each | A new block is admitted if **any** of its labels qualifies; no separate shared tier | Each label keeps100 resolved outcomes (first hit, or evicted unhit). Full window and>=5% hits admit new blocks. Later hits do not promote existing low blocks | Per-block residency/order/version/label state plus O(100L) outcome windows. Admission scans label windows (100 is fixed), not the entire cache. Heap operations normally O(log B), with rebuild/stale-pop worst cases. |

All policies continue into the highest/protected tier if no lower-tier block exists. They return an unused victim while available; an empty free table raises `No usable cache memory left`. None obtains oracle future reuse or the offline distinct-block working set. RFIFO updates resolved outcomes once per residency; physical block reuse clears old history.

Workload labels are provided by trace adapters and transported through request/sequence/block metadata. They are not predicted online. The final fix transports optional labels through `MQLLMEngineClient` → pickled `RPCProcessRequest` → `MQLLMEngine._handle_process_request` → `LLMEngine.add_request`; an absent label remains None. Integration tests inspect request and full-block metrics in both API frontends, while policy tests cover the final ordering rules.

TLRU hold uses wall-clock time, so a queued next turn can arrive after protection expires. TFIFO's static treatment of chat can be harmful when conversational prompt tokens become a larger mixture component. These are mechanisms to compare with measured outcomes, not assumed performance guarantees.

Historical M2/Task 1 event logs do not contain eviction counts; their tables use null, never zero or a miss-derived estimate. New mixed runs use an opt-in allocator wrapper (tools/comp536_counting/sitecustomize.py) to count successful eviction allocations and flush an atomic JSON record on normal server shutdown. The isolated counter check confirms one successful allocation increments once and an empty-table return does not. Promotion/protection counters remain unavailable; no inferred estimates are reported. The measurement wrapper adds Python call overhead but changes no return value, victim choice or reference count. Metadata/complexity descriptions are source-level asymptotic analysis, not measured CPU or byte overhead. Optional policy-parameter ablations were not run ahead of required experiments.
